# Exam setting foundation

This package brings the supplied past-paper importer into the repository. It
extracts and checks historical papers for use as style and structure examples.
It does not copy historical questions verbatim into a new examination. Parsing
is offline and never modifies the original source files.

## Requirements

- Python 3.10 or newer
- Pandoc for `.docx` files
- `pdftotext` for `.pdf` files
- LibreOffice (`soffice`) for legacy `.doc` files

Install `pytest` separately if you want to run the parser tests.

## Import a folder of papers

Run from this directory (`scripts/exam-engine`):

```powershell
python -m exam_engine.ingest "C:\path\to\past-papers" --out "C:\path\to\review"
```

The output contains `papers.jsonl` (the full parsed structures) and `report.csv`
(a row for every supported document, including ignored schemes/outlines and
unreadable files). Review the report before using any parsed paper.

To flatten clean papers into reference examples:

```powershell
python -m exam_engine.bank "C:\path\to\review\papers.jsonl" --out "C:\path\to\review\questions.jsonl"
```

## Review status

- `usable`: parsed without issues and matches the expected paper totals.
- `usable_with_notes`: parsed, with marks deviations recorded for review.
- `unread_parts`: one or more questions need manual correction.
- `ignored:scheme` / `ignored:outline`: retained in the report, excluded from
  the question bank.
- `unreadable`: retained in the report with the extraction error.

Only `usable` and `usable_with_notes` papers are flattened. The supplied
reference export and its source report are in `data/exam-setting/`. These rows
are not loaded into `exam_questions`: they lack a verified topic/learning
outcome and several unit codes need mapping to this installation's unit IDs.

## Database setup

Apply `supabase/migrations/20261017120000_exam_setting_foundation.sql` and
`supabase/migrations/20261017211000_exam_blueprint_lifecycle.sql` through the
normal Supabase migration process before using the workflow. The foundation
scopes all records to a department and keeps paper and generation records
HOD/system-admin only. Trainers can read notes/format guides for their
allocated units and contribute their own draft questions; historical exam
papers stay confidential. The lifecycle migration
supports department-scoped blueprint versions and atomic activation.

The app's first workflow step is the HOD blueprint manager at
`/assessment/exam-setting`. It saves draft versions using the college paper
format and supports activating/retiring versions. The remaining workflow is
followed by past-paper review, question-bank tags, paper generation, and final
moderation/export.

The second step is `/assessment/exam-setting/past-papers`. Upload the
`papers.jsonl` generated by `exam_engine.ingest`. Papers with a clean parser
status and a unique match between the parsed unit name and an active department
unit name are
registered immediately. Papers with uncertain unit matches remain in the
review queue; the HOD can auto-import any other safe matches with one action,
then manually match the remaining papers. Parser errors and ignored outlines
or marking schemes are excluded. Printed unit codes are retained as source
metadata but are never used for matching. The source JSONL artifact is kept in a private
Supabase Storage bucket and each accepted paper is registered with its parsed
structure and trainer notes.

Apply `supabase/migrations/20261018110000_exam_partial_import_and_auto_ready.sql`
before using automatic registration. It allows confidently matched records to
be committed in batches without closing a batch that still has uncertain unit
matches to review.

The third step is `/assessment/exam-setting/question-bank`. HODs can tag each
parsed question against a curriculum topic and optional learning outcome, then
set its difficulty and cognitive level. Source paper, year, marks, and a stable
question key are retained for lineage; historical questions are reference
material and the database prevents them from being approved for direct reuse.
Apply `supabase/migrations/20261018064000_exam_question_source_keys.sql` before
using this step. Questions whose marks could not be resolved remain visible for
review but are not saved until their source can be corrected.

The fourth step is `/assessment/exam-setting/generate`. It uses every readable,
marked question in the selected unit's imported archive as a source pool; Step 3
topic tagging is optional. Less-used source questions are preferred, and the
same historical question is never used twice in one paper. The server rewrites
questions through Google Gemini using `GEMINI_API_KEY` (optionally set
`EXAM_GENERATION_MODEL`). This sends the selected unit's historical question
text to Google. Generated questions and papers remain drafts, preserve a link to
their historical seed, and are checked for wording overlap. An academic reviewer
must verify scientific accuracy, answer validity, and marks before use. Apply
`supabase/migrations/20261018141000_exam_generated_paper_commit.sql` to enable
atomic saving of generated papers.
